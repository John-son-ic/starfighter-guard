| 2. 分片超 8192 关闭；非 UTF-8/二进制拒绝；同服务器另一健康连接仍可 ping 与取快照 | `oversize fragments, invalid UTF-8 text and binary frames close only the offender` |

| 观察项 | 实测值 |
| --- | --- |
| `serverTick` | `5`（一次唤醒按上限 5 步） |

> `droppedSteps` 为 54 而非 55，是因为 `floor(1000 / (1000/60)) = 59` 个可用 tick、取 5、余 54（浮点取整）。测试断言用 `>= 50 && <= 60` 的区间，避免把浮点取整写死。

**并发与容量实测**：`maxConnections:2` 下同时发起 4 个真实升级，恰好 2 个被接纳、2 个返回 `503`；拒绝握手后 `reserved` 与 `connections` 均回到 0、`rooms` 为 0；关闭一个连接后可再次接纳并回到 2。

**队列完整性实测**：填满 6 帧后提交 seq 7/8 得到 `input-queue-full`，`queuedInputs` 仍为 6；推进 6 tick 后 `queuedInputs=0`、`lastProcessedSeq=6`；重新提交 seq 7 后推进到下一个 20Hz 广播点，`lastProcessedSeq=7`，证明被拒绝的 seq 从未被记账。

## 开发过程中修正的自测缺陷

首次运行 9/10 通过，唯一失败是我自己的观测节奏问题：重提 seq 7 后只推进了 1 tick，而快照按每 3 tick（20Hz）广播且该 tick 不落在广播点，于是读到的仍是上一次快照（`lastProcessedSeq=6`）。服务端行为正确（`duel-flight` 用 `Math.max` 单调维护 ack）。改为推进 3 tick 后再断言，未改动任何断言强度，也未修改服务端。

## 已知问题 / 观察（需 Codex 知悉）

1. **快照广播节奏影响观测**：服务端每 3 tick 或事件时广播。任何「等待某个 ack 出现在快照里」的测试都必须推进到下一个广播点，否则会读到旧快照。这是广播设计而非缺陷，但后续编写服务端回归时容易踩到。
2. **连续 3 次无效消息会关闭连接**，且有效消息会重置计数。因此「无效消息也收费」只能通过与有效消息交替来验证（本文件用 60 无效 + 60 ping）。这也意味着不能用连续 120 条无效消息做基础费用测试。
3. **传输层拒绝与应用层拒绝的差异**：超限分片与非法 UTF-8 由 ws 直接关闭（1009/1007），客户端拿不到应用层 `error`；二进制帧则会先收到 `{type:'error', error:'invalid-message', fatal:true}` 再关闭（1008）。任务书已允许该差异，本报告如实记录实测码。
4. **`droppedSteps` 对浮点取整敏感**：1000ms 积压得到 59 个可用 tick 而非 60。测试用区间断言；若 Codex 希望精确值，需在服务端改成整数累加器（本批不改服务端）。
5. **未强造慢消费者**（任务书明确不要求）：`bufferedAmount > 256KiB` 的连接关闭路径仍只有代码保护，没有真实网络压测证据，不能列为实测通过。
6. **心跳未在本批重复**：既有 `tests/duel-server.test.mjs` 已用真实 `ws` 协议 ping 且不自动 pong 的客户端验证过缺 pong 断开；本批不复制。
7. **本批只验证 127.0.0.1 回环**：未验证局域网、0.0.0.0、WSS/HTTPS、反向代理后的 Origin 行为。
